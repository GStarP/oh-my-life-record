# 前端按业务能力聚合

日期：2026-08-20
状态：已采纳

## 背景

按 `domain / ports / infrastructure` 分层会把同一业务能力的类型、规则、接口和实现拆散。维护者需要先判断代码使用了哪种技术或依赖，再跨目录拼回完整行为；这种划分没有提高当前单体前端的可理解性。

项目当前更重要的边界是记录、类型模板、云端同步和本地存储等业务能力。代码是否依赖浏览器 API，不作为顶层目录的划分依据。

## 决策

- 所有业务代码放入 `src/features/`，按业务能力聚合。
- 业务类型和纯规则跟随所属 feature，不建立独立 `domain/`。
- 外部读写接口、生产实现和测试替身围绕同一个业务能力组织，不建立独立 `ports/` 或 `infrastructure/`。
- `src/app/` 只保留应用壳、路由入口和跨 feature 生命周期组装。
- 只有不含业务语义、且被多个业务能力复用的代码才能进入 `src/utils/`；固定 UTC+8 时间换算属于此类。
- 类型仍放在 `type.ts` 或 `.type.ts`，不增加 barrel 文件，导入路径直接显示依赖的业务能力。

## 取舍

顶层目录不再直接展示“纯逻辑、浏览器实现、外部接口”等技术角色；这些信息由文件名、类型和导入关系表达。代价是 feature 目录内部会同时包含多种技术形态，收益是修改一个业务能力时相关代码集中、依赖路径更短，也不会为单个实现预先建立抽象层。

## 后果

新增代码先判断业务归属，再在对应 feature 内选择文件；跨 feature 依赖必须显式导入。接口只有在真实实现和必要测试替身都需要时保留，并与所有者就近放置。项目尚未正式使用，因此本次结构收敛同时删除旧版持久化格式的迁移与兼容分支，只接受最终规范。
